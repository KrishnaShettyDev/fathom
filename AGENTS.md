# Repository instructions

Applies to every agent and contributor working in this repository.

## Read before changing code

- Read `docs/engineering/standards.md`, then the relevant feature plan and code.
- Product authority: `Marketing_OS_Complete_PRD.html`. Part 6 resolves earlier
  product ambiguities; Part 7 supplies additional release gates. Flag conflicts.
- Read `docs/plans/phase-1.md` for scope and current implementation status.
- Inspect the working tree. Preserve unrelated work; never reset it for convenience.

## Before every feature

- Write or update `docs/plans/<feature>.md` using the feature template.
- State the user outcome, requirement IDs, non-goals, acceptance criteria,
  affected boundaries, failure cases, ordered steps, and verification commands.
- Inspect existing patterns before proposing a new abstraction or dependency.
- Resolve routine implementation choices yourself. Ask only for decisions that
  materially change scope, ownership, cost, data handling, or irreversible behavior.
- Keep planning proportional. Small fixes need a short plan, not ceremony.

## Build and verify

- Implement the smallest complete, reviewable slice; keep business rules out of UI.
- Follow the standards document. Never bypass types, authorization, or failing
  checks to make a build green. Missing data is not zero; demo data is not live data.
- Never populate the application with mock brands, products, metrics, evidence,
  or exports. Use connected source data or explicit user input. Isolated test
  fixtures are allowed only in tests and must not seed the application.
- Add behavior tests for changed invariants and failure paths. Security boundaries
  require integration tests against the actual enforcement layer.
- Run the relevant checks and inspect the final diff. Report exact checks run,
  failures, unverified assumptions, and remaining work. Never claim an unrun test.
- Update the feature plan with evidence. In-progress work is not release readiness.

## Commits

- Use the user's existing Git identity. Never configure an AI author identity.
- Never add AI co-author trailers, agent signatures, “generated by” footers,
  or credit to Codex, Claude, OpenAI, Anthropic, or another assistant.
- Use concise, behavior-focused messages, e.g. `fix: reject revoked agency access`.
- Keep commits cohesive. Inspect staged changes for secrets and unrelated files.
- Never rewrite history, force-push, or discard user changes without authorization.

## Handoff

- Explain what changed, why, verification results, and material limitations.
- Keep claims concrete. Avoid quality slogans, redundant comments, and filler docs.
